# 에이전트 지침 및 규칙

## 토큰(크레딧) 절약 및 효율적 도구 사용 지침

* **도구 호출 최소화**: 단순 질문이나 이미 기존 대화에 나와 있는 매물 정보를 다시 언급할 때는 스크립트 실행이나 DB 조회 도구를 호출하지 않고 기존 문맥을 활용해 즉시 답변한다.
* **간결한 응답**: 코드 전체 출력이나 장황한 중복 요약을 피해 입출력 토큰을 최소화하고, 변경된 핵심 코드나 중요 결정 사항만 간결하게 보고한다.
* **부분 수정 지침**: 파일 수정 시 파일 전체를 덮어쓰지 말고, 필요한 특정 부분만 타겟팅하여 수정(replace)한다.
* **오류 발생 시 재시도 제한**: 스크립트 실행이나 파일 수정 중 오류가 발생할 경우, 코드를 임의로 고쳐서 2회 이상 재시도하지 말고 에러 메시지와 함께 사용자에게 즉시 리포트하여 지침을 구한다.



## 환각(Hallucination) 방지 지침

* **근거 중심 답변**: 데이터베이스(DB)나 제공된 파일 내에 직접 기술되지 않은 미확인 정보(소유자 성함, 금액 등)는 임의로 추정하거나 유추하여 사실인 것처럼 답변하지 않는다.
* **확인 불가 명시**: 누락된 정보나 불확실한 사실에 대해서는 지어내지 말고 "데이터 확인 불가" 혹은 "사용자 확인 필요" 등으로 솔직히 답변하여 검토를 요구한다.

## 데이터 보호 최우선 지침 (Data Protection First)

* **영구 삭제(Hard Delete) 원칙적 금지 및 소프트 삭제(Soft Delete) 의무화**:
  - 메모, 체크리스트, 카테고리 등 실제 사용자 데이터가 포함된 문서를 DB에서 물리적으로 즉시 삭제(`deleteDoc`, `batch.delete`)하는 로직을 일체 작성하지 않는다.
  - 삭제 동작은 반드시 `isDeleted: true`, `deletedAt: serverTimestamp()` 처리하여 **휴지통을 통한 100% 복구 경로**를 보장한다. 영구 삭제는 휴지통 내부에서 사용자가 직접 '완전 비우기'를 수행할 때로 엄격히 제한한다.
* **카테고리/폴더 삭제 시 하위 메모 연쇄 삭제(Cascade Hard Delete) 절대 금지**:
  - 상위 카테고리나 폴더를 삭제하더라도 하위 메모가 함께 영구 삭제되지 않도록 한다.
  - 하위 메모는 `[미분류]` 카테고리로 안전하게 이동시키거나, 휴지통으로 이동시켜 언제든 복원할 수 있도록 보호한다.
* **파괴적 작업 전 백업 및 안전 확인**:
  - 대량 변경, 구조 마이그레이션 등 데이터 유실 위험이 있는 작업 전에는 반드시 클라이언트/로컬 스냅샷 등 안전장치를 마련한다.

## 빌드 결과물(APK) 저장 규칙
* 완성된 APK 파일은 빌드 후 반드시 구글 드라이브 동기화 폴더인 `G:\내 드라이브\000.앱공유` 경로에 복사 및 저장하여 배포한다.
* **디바이스 즉시 원격 설치 규칙**: 만약 컴퓨터에 안드로이드 실기기가 USB 디버깅 상태로 연결되어 있는 경우(`adb devices` 상에서 인증된 기기 확인 시), 연결된 기기에 `adb install` 명령어를 사용하여 APK를 즉시 직접 설치한다. 기기가 연결되어 있지 않은 경우에는 기존 구글 드라이브 동기화 폴더 저장 방식으로 백업을 진행한다.

## GitHub 푸시 및 배포 규칙
* **작업 완료 후 자동 푸시**: 기능 개발, 버그 수정 및 검증 작업이 완료되면 별도의 추가 요청이 없어도 변경사항을 커밋하고 GitHub 레포지토리(`main` 브랜치)로 즉시 `git push`를 진행한다.

## 앱 개선 및 개발 진행 절차 (사전 브리핑 및 피드백 필수)
* **사전 브리핑 의무화**: 사용자가 앱 개선이나 기능 수정/추가를 요청하면 바로 코드 작성이나 개발에 착수하지 않는다.
* **이해 내용 자동 브리핑**: 사용자가 별도로 브리핑을 요구하지 않더라도, 에이전트가 이해한 요구사항의 핵심과 구현 계획(방향성)을 먼저 명확히 브리핑한다.
* **피드백 수렴 후 개발 착수**: 브리핑에 대한 사용자의 확인 및 피드백을 받은 후에 실제 개발 작업을 시작한다.
